## Cluster 1: Channel `--send` / body-input surface is ambiguous (file vs text, wrong flags in usage and errors)
Cuts: pc_87f0969cd45d, pc_dc0f6960e426, pc_b0805cdd1119, pc_bfcf2abafcca, pc_8dc56b392b47, pc_98f5c2d4decb (also pc_753d42a0ac83 error-text half, see cluster 3).
Symptom: `post chat <ch> --send "hello"` treated "hello" as a body FILE path and failed with an IO error; `post send` usage line showed `--body <TEXT> <FILE>` as if both were required; guessed `--body-file` failed to parse; the IO error's advice ("use --body <text>") was not executable verbatim (needs `--send --body`). Six of these are the same mistake repeated by codex after it had already hit it.
Status: **FIXED-VERIFIED.** 864ee4f. Live evidence: `post send --help` now lists three exclusive forms with `--body`, `--body-file`, stdin, positional FILE marked "Deprecated"; `post chat --help` says "--body/--body-file imply --send"; running `post chat foo --send 'hello world'` returns `exact_fix: post chat 'foo' --send --body 'hello world'` (src/cli.rs:393-471, 509-552; error text produced from 864ee4f).
Root cause: design invited it (a positional argument to a flag-shaped verb, `--send`, whose natural reading is "send this text"), plus error text that named a fix that could not parse. Code bug only in the error text; the rest is design plus help wording. Verified.
Fix shape: already done at the root (flags imply --send; positional demoted). Residual option: remove the deprecated positional FILE entirely on both `send` and `chat` so the wrong guess cannot parse as a path (it still does: `--send 'text'` is accepted syntactically and then fails on the filesystem check). That is a breaking change, so weigh against old callers. Band-aid (already in place): actionable `exact_fix`.

## Cluster 2: Shell metacharacters eat or mangle inline `--body` (backticks, `$`, `<>`, literal `\n`), and the send still "succeeds"
Cuts: pc_4b62f3965a3f (major), pc_91e1705f8c7b, pc_a689a27c47f0 (correction of the previous: not post sanitization), pc_631608a4c7fd, pc_7345015e75fe.
Symptom: `post chat --body "...`x`... -> ..."` was command-substituted or redirected by the sender's shell; `<name>` tokens vanished; `$1.63B` became `.63B`; a Codex tool call passed a body with literal `\n` sequences. Post received an already-mangled string and reported success. One cut (pc_91e1705f8c7b) initially blamed post sanitization and was corrected within 30 seconds.
Status: **LARGELY MITIGATED, inherently not fully closable.** Fixed in guidance: `--body-file` exists everywhere; `--body` help text warns about `$1.63B` and quote termination (7f3dd31, 2026-08-11); `post chat --help` warns backticks/`$(...)` "execute and splice their output"; a warn-only tripwire for watch-event NDJSON in bodies (d863a8c, src/commands/send.rs ~755); SKILL.md leads with `--body-file`/stdin. Not fixed: no detection of literal `\n` or vanished-token bodies (rg found no such check), and none is possible for expanded text.
Root cause: environment/tooling (the caller's shell expanded the text before post ever ran) plus a design that offers inline `--body` on argv at all. Post cannot see what was lost. Verified for the mechanism (the correction cut says so); inferred for the `\n` case (JSON string double-escaping in the Codex tool layer).
Fix shape (root): make stdin/`--body-file` the only documented path for prose and demote `--body` to "one short literal line, argv only" (help already does most of this); optionally warn when a `--body` value contains a literal backslash-n with no real newline, or is suspiciously short relative to a subject (cheap heuristic, low value). Do not add sanitization. Band-aid: skill/brief guidance, already present.
