# Review: read-time lineage and participant mentions

**Verdict: merge after named fixes.** The main routing change reaches the existing mention consumers, but code spans still trigger mentions and the new tests do not guard that requirement. This is a static review of `git show HEAD`; no tests, builds, Cargo, or Node commands were run.

## Findings

1. **Medium — code spans ring participants.** `MentionTargets::addressed_by` calls `extract_mentions` on the full raw body (`src/channel.rs:1532-1537`). That scanner checks the characters around `@`, but has no code-span or fenced-code state (`src/channel.rs:1450-1490`). A body such as ``Use `@sieve` in the example`` therefore yields a mention; watch emits `reason: mention`, the doorbell treats it as eligible, and chat/peek/catchup/crossed count it. The sender-side workspace scanner already has this behavior, so the rule is reused faithfully, but extending it to lineage and participant ids expands who can be woken by example text. If code spans must be excluded as requested, fix the shared mention rule consistently for stamping and read-time resolution, and add inline and fenced-code cases (including an actual mention outside the code).

2. **Medium — the new tests leave key negative and consumer cases unbound.** `tests/lineage.rs:1889-1923` does bind unstamped `@sieve` and `@<participant id>` to watch `reason: mention`, and binds the `@sievex` negative case by asserting exact event ids. `tests/lineage.rs:1925-1944` binds an unstamped lineage tag to crossed `addressed_to_you`: the fixture has no registered `trey` owner room or `owner.json`, so the owner exception cannot make it pass. Both rely on an unstamped fixture, so the first test in particular would fail if read-time matching were removed. Neither test covers `a@sieve.com`, case changes, code spans, peek rescue, omitted counts, degraded watch, or the room-only watch path. Add focused negative cases and at least one peek/omission assertion; the code-span case should be red until finding 1 is fixed. The commit message's claim that tests were run or red with scanning disabled was not independently verified here.

## Requested checks

- **Boundary and case:** The new lookup reuses `extract_mentions`, so its Unicode-aware case-sensitive boundary rule is exactly the workspace rule (`src/channel.rs:1450-1490,1541-1545`). `a@sieve.com` is rejected because the preceding `a` is a word character; `@sievex` is rejected because the following `x` is one. `@Sieve` does not match `sieve`. Code spans are the exception above.
- **Completeness:** Crossed uses `MentionTargets` (`src/channel.rs:1309-1321`); watch's participant and degraded scans use it (`src/commands/watch.rs:1619,1767,1918,1966`); room-only watch calls `WatchEvent::channel_message` with the body (`src/commands/watch.rs:2132-2138`, `src/output.rs:1531-1559`). Chat's two omitted-count paths and peek rescue use it (`src/commands/chat.rs:692,746,855,1012,1217-1265`); catchup's omitted count uses it (`src/commands/catchup.rs:795,855`). No remaining `mentions == room` comparison was found in `src`. The doorbell supervisor and hook notices consume Post watch's `reason` directly and already accept `mention` (`skills/post/hooks/doorbell-supervisor.mjs:381,490,563-564`; `skills/post/hooks/watch-notice.mjs:178-179`), so they need no body scanner. `post inbox` counts direct mail, while `post channels` exposes total unread channel messages (`src/commands/inbox.rs:114-130`; `src/commands/channels.rs:38-55`); neither has an unread-mention count to switch. No missed consumer found within these surfaces.
- **Performance:** No new body file loads were found. Crossed's `unread_channel_with` already returns body; chat's `read_batch_participant` and cursorless collector already hold bodies; catchup remainder items already hold bodies; watch already parses full messages and uses bodies for previews (`src/channel.rs:1310,1317`; `src/commands/chat.rs:1717-1760`; `src/commands/catchup.rs:851-861`; `src/commands/watch.rs:1764-1778,1963-1977,2111-2140`). There is new CPU work: each addressed check without a matching stamp searches the body and sorts up to three target names; the target set itself is built once per scan. The cost repeats on watch reconciliation, peek selection, and byte-budget suffix counts; it is linear in body length per checked message, with no benchmark in this review.
- **Safety:** A sender can include every known lineage/id in one body and cause eligible mention events for all matching readers. This broadens an existing capability: a sender could already tag every registered workspace. The doorbell still applies its mute and subscription rules; mentions bypass channel subscription but not mute (`skills/post/hooks/doorbell-supervisor.mjs:483-493`). The new read-time scan does not gate sending. Crossed calculation is best effort and errors become warnings before the append (`src/channel.rs:946-976`), so the added mention resolution cannot itself make a send fail. Existing send validation and storage errors remain possible.
- **Contract:** `CONTRACT.md:608-618` and the chat schema text describe the three target names, case-sensitive boundaries, unstamped old senders, and affected outputs accurately. They do not promise code-span exclusion. The statement that mentions never fail a send matches the send path. The older output comment at `src/output.rs:1396` says only the watching room can produce `reason: mention`; update it to include participant id and lineage when fixing the above.

**Named fixes before merge:** define and implement the requested code-span exclusion in the shared matcher; add tests for code spans, emails, case, and a read-side peek or omitted-count path; update the watch reason comment. Recheck the documented behavior against those cases.
