## E. The `target/release/post` question (Trey's gate fact)

Do the tests or the gate docs handle a managed cargo target dir? Answer: the gate script and the launcher tests do; the hook contract tests, CONTRIBUTING, README, and acceptance.sh do not.

- Handled, launcher tests: `launcher/agent-session.test.mjs:13,18` take `BIN = cargoReleaseBin(REPO)`, which asks `cargo metadata` for `target_directory` (`scripts/cargo-release-bin.mjs:6-15`). Added by `98d53c4` (2026-09-05) for exactly this class of failure. So the launcher tests do NOT assume `target/release/post`; the premise in the task note is off for `launcher/*.test.mjs`. Only the test header comment (:2) says "cargo build --release && node --test launcher/agent-session.test.mjs".
- Handled, gate: `scripts/gate.sh:39-42` resolves the same path and exports `POST_BIN` before the hook suites, the schema step (:56-58) and the bridge suite (:65-67). Comment at :33-38 says why. Under the gate, `POST_BIN` is therefore set by the script itself, not by the operator.
- Not handled, hook contract tests (area 17 files, read only for this question): `skills/post/hooks/contract.test.mjs:34`, `doorbell-supervisor.test.mjs:43`, `doorbell-supervisor-process.test.mjs:20` default to `<repo>/target/release/post` and never call the resolver (`contract.test.mjs:6`: "POST_BIN selects the producer (default <repo>/target/release/post)"). A missing binary fails loudly (never skips), but `node --test skills/post/hooks/*.test.mjs` run by itself, as CONTRIBUTING.md:10-13 lists it, fails on this box unless `POST_BIN` is set. That matches what was seen today if the node suites were run outside `gate.sh`.
- Not handled, docs: CONTRIBUTING.md:14 (`target/release/post schema >/dev/null`) and README.md:39 (`install -m 0755 target/release/post ...`) hard-code the path; the hook repair message (`claude-mail.test.mjs:708`, same in codex/grok) tells users to `install -m 0755 target/release/post ~/.local/bin/post`. No document mentions `POST_BIN` for the hook suites, the managed target dir, or `estate-build-cache`. `docs/RELEASING.md` is silent on it.
- Not handled, `tests/acceptance.sh:113`: `bash scripts/smoke-installed.sh target/release/post` (suspected bug S2).
- Handled independently, install: `scripts/install-post.sh:186-190` resolves the target dir with `cargo metadata` and `install_post.rs:365` pins it; the Rust tests use `CARGO_BIN_EXE_post`, which cargo sets, so they are unaffected.
- Unverified hazard (needs a run, see open questions): the estate cargo wrapper picks a build slot per invocation (`plan`/`select_slot` in `estate-build-cache`, roughly lines 90-160) and injects `--config build.target-dir=<slot>` (`command`, ~lines 160-185). `gate.sh:31` (`cargo build --release`) and the later `cargo metadata` inside `cargo-release-bin.mjs` (called at `gate.sh:39`) are separate invocations. If another lane holds the first slot at one moment and not at the other, the resolver names a slot the release build did not use, and the gate (which does not compare build ids, unlike `install-post.sh:196-198`) could run its node suites against another lane's binary. Both would normally choose slot 0, so the failure is intermittent.
