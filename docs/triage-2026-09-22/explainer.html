01

Contract drift: post's output has many strict readers and no shared tests

highest leveragerefactor
Post's JSON is read by Porch, the Python doorbell, the Codex monitor, the Claude/Cursor/Grok hooks, and the skill docs. Each one validates the shape its own way. When post changes one field, a reader somewhere breaks, and nobody finds out until something stops working. It happened tonight with Porch. It has been happening quietly with the Python doorbell since participants shipped: post deliberately leaves room off participant-addressed mail, and the doorbell requires it.

Band-aid now

  • Python doorbell: take the mail namespace from address.kind/name when room is absent.
  • Point the bridge reference at a stable, versioned URL for SPEC-v2, not a devbox-only path.

Real fix

  • Post ships contract fixtures: golden samples of every event and every --json output that other tools read.
  • Every reader tests against those fixtures in its own suite, so a post change that breaks Porch goes red in Porch's tests first.
  • The install smoke runs the readers' startup checks (Porch's launch check, the doorbell parser) before an install counts as done.
  • The skill carries a contract version that post doctor compares against the binary.

02

Five separate doorbells, all of which fail silently

most user-visiblerefactor+ feature
Waking an idle agent is done five different ways: a Claude Monitor, per-harness hooks, a Python daemon, a Codex systemd timer that drives herdr, and Cursor/Grok wrappers. Each has its own filters, lifetime, and failure handling. They share one habit: when delivery can't happen, they do nothing and say nothing. A timer whose pane is gone just keeps running. Error messages drop the reason ("snapshot failed; notification state is unknown"). Claude's Monitor expires without a trace.

03

Watch re-reads the whole store on every wake

refactor · large
Every wake-up re-lists every channel file and re-parses the whole inbox, so a doorbell's CPU grows with history and with how busy everyone else is, not with new mail. The sweep's theory that watch "spins in a loop" is outdated; this is simply the cost of the work it repeats. Post already skips parsing channel messages you've seen.

First step

  • Measure: time mail scans and channel listing separately, on a real heavy participant.

Real fix

  • Keep an index of what's unseen for each watcher, updated from file events, with a periodic full pass as a correctness backstop. The periodic pass guards the edge cases this could otherwise miss: renames, overflow, files arriving from the bridge.

04

A bad cursor file turns into "everything is unread"

mostly mitigated
Writes are safe: post writes a temp file and renames it into place. Reads don't take the lock, though, and they check the file and then read it in two separate steps, so a race can make a valid file look broken for a moment. Current code already retries once, names the path and the reason in the warning, and flags a digest built from bad cursor state as a re-report rather than new mail. The "339 new" false alarm should no longer look like a real burst.

Now

  • Nothing urgent. Make sure every doorbell shows the re-report flag instead of ringing on it.

Later

  • Open the file once and check that same open file, to close the race. Keep failing open: never auto-reset read history.

05

A send can hang after it has already landed

behavior change · small
After a channel message is written, post marks it as seen for you. That step waits on a file lock with no time limit. If another process holds the lock, your terminal hangs even though the message was delivered. That's a live mechanism for the August "11-minute send" report.

Fix

  • Give that wait a deadline. If it expires, print a warning and return the send receipt. Nothing is lost: the message is already written.

Follow-on

  • One shared lock helper with a deadline for every blocking lock in post, each with a defined outcome on timeout.
src/commands/chat.rs:2260-2336 · src/cursor_state.rs:362-394
06

The CLI guesses what you meant

band-aids
echo hi | post chat ops reads the channel and throws your text away, because only --send/--body count as send intent. post who prints state=active for a lease that hasn't expired, and readers take it to mean the agent is working; that belief once held a launch for 30 minutes. The installers reject --help because it hits argument validation first.

Fixes

  • Piped input on a read → refuse, and hand back the exact --send command. Never auto-send: a missing flag shouldn't be able to deliver anything.
  • state=active → lease=active, plus a hint pointing to --seen-by, which is the tool that actually answers "did they read it?"
  • Installers: handle --help first, exit 0.

Already fixed

  • Shortened ids now print the shortest prefix that's unique in the channel, plus a "…", and every flag that takes an id accepts it back. Closed tonight.
07

Registries without the verbs to maintain them

new feature · medium
Rooms and sigils live in JSON files, and the only tool for changing them is editing by hand. Moving brief-app from the Mac to the devbox meant hand-editing rooms.json, and choosing a sigil is trial and error.

Build

  • post rooms set-path NAME PATH, under the registry lock, with checks.
  • post profile list: who holds which sigil, using the same lease rule that enforces uniqueness.

Hold

  • Renaming a room is its own design: history, memberships, routes, and old references all point at the name.
