# Lane C — cross-host design diagnosis

**VERIFIED:** the bridge source already publishes real room names, registers placeholders from peers' `rooms.json`, and has channel archive import/publication behind a separate config gate. **INFERRED:** the smallest native Mac→`#loom-build` slice is to confirm `loom` room publication, then allowlist only `loom-build` on both hosts. The missing Mac `loom` entry is not caused by `channels: null`; its incident-specific cause depends on live publication/topology state, which this read-only pass could not inspect. A remote participant DM needs a separate address contract because Post participant IDs are local records and the bridge transports room-addressed mail only.

## Per item

### Missing or stale remote room placeholders (Mac `loom`)

- **ID(s):** No matching cross-host room item appears in `review-input/open-cuts.jsonl`; scoped from Lane C request.
- **Symptom:** Mac `post rooms` has no `loom` placeholder (or only a small/old set of `remote/<host>/<room>` registrations).
- **Root cause:** **VERIFIED** — room publication is generated from `post rooms --json`, excluding paths under `remote/`, invalid names, and publisher-denied names; peers are discovered from each registered host's `rooms.json` at the fetched branch OID; only un-contested published/pinned names become routes and placeholders. See bridge `bridgelib/rooms.py:322-358, 385-455, 617-640`; placeholder registration is `:523-614`. Retired placeholders are intentionally retained rather than deleted (`:437-440, 523-545`). The null channel setting does not enter this room path.
- **Fix class:** behavior-change (conditional on a verified code defect; if room publication/config explains it, no code change is warranted).
- **Proposed direction (INFERRED):** Check the devbox's committed `rooms.json` for `loom`, its `post rooms --json` real-room registration/path, local room deny inputs, whether the Mac's bridge has fetched that branch revision, and its `bridge/rooms/owners.json` contest/owner state and health. If `loom` is absent from the branch, fix the publisher's room registration/publication; if present but not on the Mac, repair/update the receiving bridge topology. Don't hand-add a permanent placeholder: it can mask a stale publication and won't establish an outbound route.
- **Effort:** S to diagnose from current branch/config evidence; M if a reproducible importer defect remains.
- **Risk:** Manual placeholder/config edits can leave path and owner state inconsistent; stale branch refs can make a healthy publisher look broken. The bridge intentionally retains retired placeholders, so a stale `post rooms` listing alone does not prove stale routing.

**Current evidence limit:** the devbox bridge clone is `post-bridge-v2` at `db01766`, 18 commits ahead of its remote, with pre-existing staged edits to bridge source; it has no cached `origin/machines/*` refs. I did not fetch, inspect either host's live mail-root config, or inspect the installed bridge package. I therefore cannot tell from this read-only source pass whether the Mac symptom is specifically an unpublished devbox room, a stale fetched branch, an ownership/contest state, or a runtime deployment lag. The source path and diagnostic split are verified; the incident-specific branch state and deployed behavior remain unverified.

### Channel sync is disabled; enable only `loom-build`

- **ID(s):** No matching cross-host channel-sync item appears in `review-input/open-cuts.jsonl`; scoped from Lane C request.
- **Symptom:** `channels` is null on both bridge configs, so neither host imports nor publishes channel archives.
- **Root cause:** **VERIFIED** — `parse_channels_config(None)` returns no config and `channel_allowed(None, name)` rejects all channels (`bridgelib/channels.py:80-118`); both `import_channels` and `publish_channels` return empty stats when config is absent (`:1270-1296, 1690-1695`). The spec says this optional key is absent/off for exact v1 behavior while `rooms.json` remains on (`SPEC-v2.md:357-377`); the wiring landed as an optional field in `f3c0549` (“Wire v2 configuration into the sweeper”).
- **What was risky:** **VERIFIED** — a receiver-side deny cannot hide fetched channel bytes from relay hosts because Git fetch places publisher history in `.git`; a channel that must remain private must be denied at every publisher (`SPEC-v2.md:370-377`). Import deliberately leaves Post cursors alone, so backfilled messages become unread (`:512-515`), and imported join events can add registered participants to channel membership subject to the receiver's local rules (`:479-510`). The earlier Sol review found a blocked-route admission gap and concurrent channel-index mutation risk; r5.3 records the repaired rules check and Post channel lock (`reviews/review-sol-v2-r5.0.md:162-178`, `SPEC-v2.md:479-510`). The self-echo path is designed around `(channel,id)` received reservations and immutable archive bytes (`bridgelib/channels.py:1273-1292`, `SPEC-v2.md:450-478`); I found no current reason to treat loops as an unresolved blocker, but this clone was not runtime-tested.
- **Ordering/archive/cursor details (VERIFIED):** the bridge imports per host, channel, then sorted message ID (`SPEC-v2.md:424-430`); channel IDs include microseconds, but a same `(channel,id)` with differing bytes becomes an explicit divergence fault rather than an ordering winner (`:498-510`). Channel history is append-only and never pruned; each tick checks the peer diff for deletion/rewrite before importing (`:323-337`). Bridge page cursors are separate from Post read cursors. Post cursors are untouched, so first backfill remains unread (`:512-516`). Imports reserve IDs before publishing files and replay idempotently; publication recognizes received IDs, preventing imported messages from echoing back (`:389-407, 451-463`).
- **Fix class:** behavior-change (opt-in config activation changes the existing bridge behavior; the import/publish implementation already exists).
- **Proposed direction (INFERRED):** At both devbox and Mac, set `channels` to `{"mode":"allow","allow":["loom-build"]}`. This is the narrowest bidirectional policy: the sender must publish and the receiver must import. Keep confidential channels out of every publisher allowlist (receiver deny alone is not confidentiality). Before activation, inspect `loom-build`'s current channel record, membership, and backlog; expect the first import to make history unread. Verify one post each way, a join event, and a second-tick no-op before wider rollout.
- **Effort:** S for config activation and controlled smoke; M if live behavior differs from source.
- **Risk:** Allowlisting at only one host creates one-way or no sync; first-seen backfill can trigger unread/mention behavior; relay principals can inspect any published channel's fetched history. Membership synchronization is intentionally not an implicit join-all: it replays join records.

### DM to one named remote participant

- **ID(s):** No matching cross-host participant-address item appears in `review-input/open-cuts.jsonl`; scoped from Lane C request.
- **Symptom:** Mac cannot address one devbox participant by its local ID; the workaround chooses the destination host context via SSH and runs `post chat` there.
- **Root cause:** **VERIFIED** — Post resolves `participant:<id>` only by looking up a participant in the current local store (`src/participant.rs:275-310`); participant inbox paths are rooted at the local `participants/<id>/inbox` (`:249-272`). The bridge envelope requires a string `to`, validates it as a room, and requires it to equal the path's expected room (`bridgelib/common.py:55-58`; `sweep.py:585-623`). Outbound routing maps that room through the published room topology (`sweep.py:1245-1263`). A participant id therefore has neither global uniqueness nor a remote host binding in the current address contract. Existing `sender_address` data is sender metadata, not a remote recipient route.
- **Fix class:** new-feature; bridge plus Post address/routing contract.
- **Proposed direction (INFERRED):** Prefer a typed remote target such as `participant:<id>@<host>` over making workspace lookup impersonate participant routing. Parse this as a distinct host-qualified address, validate `<host>` against the enrolled registry, relay through a dedicated participant-recipient envelope field, then resolve the id against the destination host's local participant registry and deliver to that participant inbox. Preserve ordinary `workspace:<room>` addressing unchanged. Do not silently fall back from missing participants to a workspace inbox.
- **Effort:** L for robust general support; M for a tightly scoped bridge recipient envelope if Post's user-facing parser already allows a compatible form.
- **Risk:** Stale/reused participant IDs, host claims, privacy of participant traffic in relay history, and inbox lifecycle must be specified. If a participant has ended or moved, route failure must be explicit. A room-plus-participant envelope could preserve the room as stable outer route, but adds two identities and risks confusing a workspace-wide delivery with a private participant DM.

## Addressing design options

| Option | Direction | Trade-offs |
|---|---|---|
| `participant:<id>@<host>` | **INFERRED:** Add a host-qualified participant address and carry `{kind: participant, id, host}` through the relay; destination resolves the ID locally. | **Recommended (INFERRED).** Direct and explicit; participant IDs can remain host-local. Requires a new Post address variant/parser and bridge envelope/receipt validation. Must reject unknown hosts and absent/ended IDs; cannot use room-only routing unchanged. |
| Host-qualified workspace plus participant recipient | **INFERRED:** Route to a published workspace on `<host>` and attach a participant recipient that the destination delivers to its local participant inbox. | Reuses the existing host/room outer route and helps when a participant has a meaningful home workspace. Couples delivery to room ownership/moves and risks confusing workspace-wide mail with a private participant DM. |
| Publish participant directory globally | **INFERRED:** Publish participant IDs, workspace, lineage, and lifecycle so senders can resolve names before sending. | Better discovery, but exports session/agent metadata, grows stale between ticks, and requires identity lifecycle/ownership rules. Larger and riskier than the stated single-recipient case. |

**First-slice boundary:** channel participation and participant DMs should not be forced into one rollout. For the requested Mac→`#loom-build` case, first enable only that channel in both bridge configs, verify the `loom`/`loom-build` distinction (workspace name vs channel name) and devbox room publication, then run a bidirectional channel smoke with the Mac otherwise offline. Follow with a host-qualified participant-recipient envelope using one known devbox participant; leave global participant discovery for a later decision.

## Shared root-cause clusters

1. **VERIFIED — separate namespaces and gates:** `rooms.json` publishes workspace names; `channels` controls channel archives; Post participant addresses are local. Turning channels on cannot create a `loom` workspace placeholder or make a participant ID global. A unified topology/address contract is a possible future refactor, but the first slice should preserve these distinctions.
2. **VERIFIED — per-host topology:** the peer registry, published `rooms.json`, ownership memory, and fetched branch OID jointly determine routes. **INFERRED — incident alternatives:** publisher registration/publication, unrefreshed receiver refs, or intentionally retained retired placeholders could explain a missing/stale listing; changing placeholder creation alone would not address all three.
3. **VERIFIED — channel privacy boundary:** channel allow/deny controls archive transfer, while relay Git visibility is determined at the publisher. Receiver filtering is not confidentiality. This is independent of room routing and participant addressing.

## Recommended order and what not to fix

1. **Verify the live room publication chain** on devbox and Mac: devbox real `loom` registration and published `rooms.json`; Mac fetched branch OID, `bridge/rooms` health/ownership/contest state, then `post rooms`. Fix the first broken link found. Source-only diagnosis does not establish which one failed today.
2. **Enable `loom-build` in allow mode on both hosts** after confirming the channel contents are appropriate for every relay principal and accepting unread backfill. Verify read/write both ways, membership/join, and second-tick idempotence.
3. **Design a participant-address envelope** with explicit host binding, destination-local ID validation, delivery/receipt semantics, and ended/unknown-target errors. Implement only after the channel slice proves the bridge round trip needed for this collaboration.

Do not fix by enabling `mode: all`: it publishes every eligible local channel and widens relay-history exposure. Do not manually add `loom` to the Mac's rooms list until confirming the publisher publication and owner state; that can mask the missing link. Do not auto-delete retired placeholders: the spec retains them to avoid stranding queued mail and reopening name squatting. Do not globally publish participant/lineage inventories for this one DM; their disclosure and stale-lifecycle costs are not justified by the case.
